# CUIMS empty-sidebar investigation — 10 October 2026

Investigated the shipped Firefox 0.10.3 (`35b1c45`), rather than the original checkout's 0.9.1. Changes are isolated on `diagnose/cuims-rate-limits` in `work/rate-investigation`. No store upload, version bump, new dependency, credential change or leave submission was made.

## Findings

CUIMS can return **HTTP 200 at the requested URL with an empty navigation menu**, without a login form, error URL, rate-limit message or rate headers. This is the user's reported failure shape. In the live Firefox extension-context experiment, the medical-leave response at `06:06:59.316 UTC` had three portal links instead of 85. Home at `06:07:48.623 UTC` also had three links, with `#uims_sidebar` present and `#menu-content` present but containing zero children and zero links. It was still empty at `06:11:32.868 UTC`.

The existing client classified that response as success. Regression tests reproduced three consequences: an optional leave read replaced cached applications with an empty list; a timetable read sent its fallback POST; a home check reported a usable session. An empty menu does not prove a signed-out session, and should not trigger a login attempt.

A separate regression reproduced stale coordination: a tab's page load or refusal during an attendance report was invisible to optional reads because their admission clock captured storage at the start of the run. An invalid cached report could also reopen attendance after a tab had just reported a refusal.

The empty-menu onset was the **30th instrumented inner-page fetch in this mixed experiment**, over roughly 13 minutes. This is an observation, **not a verified limit of 30 per 10 minutes**. The experiment did not begin from a proven empty server counter and does not capture every native-tab request, redirects, other browser/account traffic or server-internal work. No response supplied a numerical quota or reset time. It does not establish whether the restriction is per account, session, IP, page type, rolling window or burst heuristic.

Three rapid sequences failed on their third page. The final sequence requested attendance alone, so duty/medical leave is not required to reproduce the failure. Together with the healthy twelve-read sequence using five-second waits, this supports a burst-sensitive restriction. It does not establish the precise boundary between three and six seconds, a universal quota, or the absence of additional server rules.

Burst probes ended at `06:28:43.599 UTC`; the diagnostic popup was closed and its outstanding work aborted. After a quiet interval, a single ordinary timetable reload around `06:45 UTC` displayed a populated sidebar. A subsequent inspection surfaced an error page and an empty-menu attendance response, but this was not a fresh instrumented request. The user clarified that it was old state and confirmed normal loading. An observation without navigation around `06:48 UTC` confirmed the attendance page, populated Academics/Profile sidebar links and no error. **The native portal was recovered at that point.** Do not count inspection of the old response as another measured refusal or infer a fresh transition from it. The later ordinary-use failure is recorded separately below. No further burst probes followed the final stopped sequence.

One earlier attendance probe used `type=Student` instead of the release query, redirected to `error.html`, and was followed by a healthy request using the exact release query. Exclude it as proof of throttling. A diagnostic typo also called `/StudentAttendanceSummary.aspx/GetReport` and returned 404; it is retained in the trace for transparency and excluded from valid attendance-report counts.

The extension's old `40/10 minutes` and current `25/10 minutes` are **local safeguards**, not CUIMS-published or empirically verified quotas. Lowering the total alone cannot correct an unrecognized HTTP 200 refusal.

## Update and duty-leave questions

Updating does not erase the attendance/report metadata, timetable, leave cache, budgets or backoffs. Startup clears stale run locks and working state. An upgrade can make some history or a missing leave category due, adding work on the next refresh; that is different from a full cache reset.

Duty and medical leave already existed in 0.8.7 as well as 0.9.0/0.9.5. Those versions alternated one leave page every three hours combined. In 0.10.3, each category is due independently every three hours, spaced behind other page traffic. This increases their potential daily page count; it does not establish duty leave as the sole cause of today's failure. The differential harness includes the verified 0.8.7 parent of `11b4462`.

0.8.7 had no periodic network timer: the Attendance view fetched when opened with a cache older than ten minutes. Its thirty-second interval repainted the UI. The forty-request budget was not forty scheduled requests every ten minutes.

0.10.3 also refreshes once when a popup opens with attendance older than ten minutes, and schedules the missing-timetable follow-up. It is not completely manual. The live installed popup had ten subjects' history and a 36-slot timetable, and its opening refresh sent one attendance report. The offline warm-upgrade comparison did not reopen attendance or log in, but did read newly due history and medical leave.

Leave lists can be read directly through the existing signed-in session without the user opening the leave page. They still require a page request; background fetching cannot eliminate that server work.

## Implemented second candidate

- The shared request client recognizes the observed protected-page markup with an empty `menu-content` list and enters the existing page pause. It stops before parsing leave data, timetable postbacks or a successful home-session result. Initial login responses are excluded because their menu has not yet been initialized.
- The tab recognizes the same symptom after DOM loading, stamps the shared refusal clock, and avoids processing the empty page as a successful session or leave update.
- Optional reads consult current tab activity/refusals instead of the initial storage snapshot. An invalid report's attendance-page fallback also rechecks the current refusal clock.
- Every individual portal-page request, **including Home**, now waits at least six seconds after preceding background or observed native-tab page activity, including cold login landing/attendance steps and legacy timetable GET/POST pairs. Admission rereads shared activity and refusal state after waiting; a newly active login tab wins ownership. This is a conservative local policy, not a claimed server threshold. Saved report calls are not delayed by this gate.
- Open CUIMS reuses the known signed-in cookie session even when its last observation is older than the two-minute background preflight window. The visible destination validates that session; normal native login handling remains available if it expired. Successful timetable reads update session knowledge. Saved cookie-omitted reports alone cannot establish that the portal session works.
- The visible Open CUIMS destination waits in the same admission queue. An existing page pause prevents another Home check or broken tab load; a refusal arriving during the wait cancels opening. These changes remove the redundant hidden Home read from the captured workflow.
- Raw-response callers, including LMS SSO, also detect an empty Home menu by inspecting a cloned response. The original body remains available to the caller. A new refusal starts the page pause; a blocked attempt during an existing pause does not extend it.
- Chrome is synchronized from Firefox. Attendance, history, forecast, timetable, duty leave and medical leave remain available. The existing report path remains usable during a page pause; cached leaves and timetable remain intact.

This patch handles a reproduced refusal and coordination defect. It does not prove that CUIMS will stop refusing requests, or that the underlying server counter has been identified.

## Feature-preserving workflow

Keep showing cache immediately and refresh attendance through saved report identifiers. Coalesce concurrent refreshes and retain the minimum interval and persistent request budget. Read history incrementally rather than discarding it after an update.

Treat attendance reports and session-bearing page reads separately. Put timetable and leave page reads behind one serialized admission policy shared with CUIMS tabs. Keep the existing five-minute clearance from page activity while the true server policy remains unresolved; allow at most one optional page task per refresh. Legacy timetable markup may require a GET and POST within that task, so budget and pace both. The six-second gate can add roughly twelve seconds to a cold login and six seconds to a legacy timetable postback. Warm cached report reads retain their fast path. An optional leave read may move to a later eligible refresh as the paced timetable shifts the existing five-minute clearance; the differential trace verifies the same eventual feature requests and counts as 0.10.3. The current live timetable already renders on its GET.

Stop page work on a redirect refusal, explicit throttle or the observed empty-menu response. Preserve the last usable feature data and show its age. Do not convert a missing menu into an empty leave history, loop through login, or disable otherwise working report reads. The existing page pause starts at fifteen minutes and escalates on repeated refusal.

A periodic background scheduler should use the same queue and persisted state, refresh reports while identifiers work, and fetch due leave pages only when the session and page admission allow it. Restoring periodic work is a separate release gate: first measure a quiet-session sequence and recovery, then validate that scheduler with ordinary portal use. No new periodic timer or speculative numerical CUIMS quota is included in this patch.
